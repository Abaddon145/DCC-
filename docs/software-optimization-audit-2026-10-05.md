## 优先修正的现有流程

### P0：大媒体读取时的内存与锁占用

- 证据：`src-tauri/src/lib.rs:115` 注册媒体协议；在 `state.with_library` 内调用媒体响应函数。`src-tauri/src/state.rs:475` 的锁覆盖整个闭包。
- `src-tauri/src/media.rs:678` 的 `protocol_response` 及 `:723` 附近的 `file_response` 都返回 `Response<Vec<u8>>`，通过 `take(count).read_to_end` 读取请求全部内容。16 MiB 只是初始容量，不是读取上限。没有 Range、或 `bytes=0-` 时，count 可为整个文件大小。
- 无效 Range 解析失败后退回完整 200 响应；后缀范围未处理，需补齐协议语义，而不是靠 UI 限制掩盖。
- 推断：大视频、模型或贴图可能增加内存压力，并在文件读取期间阻塞需要同一库锁的操作。这是代码级风险，不是本轮已经确认的闪退根因。
- 建议：在短锁内完成 UUID、库身份与登记文件校验，再用经过验证的文件句柄读取；研究 Tauri/WebView2 的受限分段响应，区分播放器与要求完整模型包的加载器。不能简单截断 200 响应冒充完整模型。保留现有路径安全与切库隔离。
- 验收：大文件打开期间导航/搜索仍能响应；合法范围、后缀范围、无效范围、关闭后读取、切库与内存峰值均有检查。

### P1：静态模型预览负担与反馈

- 证据：`src/components/ModelViewer.tsx:76` 启用 `preserveDrawingBuffer`；`:104` 即使没有动画也持续 rAF 渲染。现有实现会释放几何体、材质、纹理和 WebGL 上下文，不能说“完全没有释放资源”。
- 目前有纹理/加载错误提示，但缺少明确的加载阶段、取消读取和 WebGL context lost 恢复反馈。
- 建议：静态预览按需渲染，阻尼期间继续刷新、稳定后停止；模型加载/视角/尺寸变化触发刷新；关闭取消可取消的读取，不能取消的解析使用过期结果丢弃；增加读取/解析/贴图阶段与显卡重试，不显示虚假百分比。评估截帧是否必须长期保留绘图缓冲区。
- 一手依据：[Three.js 官方按需渲染示例](https://github.com/mrdoob/three.js/blob/dev/manual/pages/rendering-on-demand.html)。复用已安装 Three.js，不换一套查看器。
- 验收：静止、拖动、阻尼、缩放、切换、截图与后台标签状态分别测 GPU/帧数；不能承诺未测量的加速倍数。

### P1：启动包与任务空闲开销

- 证据：`src/App.tsx:13` 已对知识库使用 lazy；媒体/项目/AI 等仍静态导入，`TaskCenter → ModelThumbnailTask → ModelViewer` 又静态引入三维加载器。现有交付说明仍记录大 chunk 警告。

- 验收：记录冷启动时间、首次进入模型/知识库时间、空闲 CPU 和 IPC 请求数，再判断是否达到目标。

### P1：读取失败仍有局部被当成“没有内容”

- 证据：`src/components/GlobalNoteSearch.tsx:7` 搜索异常被空 catch 吞掉；`src/components/MediaLibraryView.tsx:207` 的媒体详情项目/参考板选择列表失败时置为空列表。

- 验收：断开/模拟失败时不显示“没有项目/没有笔记”误导，重试不覆盖较新的选择或库。

### P1：带多个点的媒体文件名格式筛选

- 证据：`src-tauri/src/media_library.rs:448` 的筛选与 `:410` 的返回格式都使用 `substr(m.original_name,instr(m.original_name,'.')+1)`，取得第一次点之后的字符串。例如 `bridge.v2.glb` 得到 `v2.glb` 而不是 `glb`；既可能影响格式显示，也可能漏掉筛选结果。
- 建议：复用导入时的规范格式信息，或统一按最后一个扩展名判定；加入多点、大小写与无扩展名回归。修正格式筛选属于明确缺陷修复，不需要用户重新决定设计。

## 真正有增量价值的功能方向

1. **统一搜索入口**：现有素材搜索附带前 5 个笔记结果，但媒体、项目、任务仍分开查找。利用已有 SQLite/FTS 和 UUID 导航，统一分组结果与键盘跳转；不把所有领域拼进单个大表，不引入云搜索。
2. **UE5 贴图集检查**：用户明确关联 Base Color、Normal、Roughness、Metallic、AO，支持 RGB/A 分通道、ORM 预览、尺寸和缺图检查，输出导入建议。不凭文件名静默认定通道含义，不改原图，不直接读写 `.uasset` 或 UE 工程。
3. **模型体检**：显示网格/三角面/材质/贴图尺寸、缺失依赖和 glTF 校验结果，便于在正式放入 UE 前判断风险；GLTF 校验不能声称同时验证 FBX/OBJ/STL，更不能保证 UE5 与 Three.js 渲染一致。
4. **离线相似图整理**：SHA-256 精确重复已有；新增感知相似候选、并排比较、用户确认。不自动删除，也不把哈希相似等同语义相似；先仅处理图片，后台可取消。
5. **参考图局部标注**：在已有参考板加少量箭头、框和备注，帮助记录构图/光照/材质分析；保持源图与笔记独立，不引入第二套无限画布。

贴图建议的一手来源：[UE 纹理通道与 mask/sRGB说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-texture-masks-in-unreal-engine)、[UE PBR 材质说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/physically-based-materials-in-unreal-engine)。具体通道顺序由用户/预设确认，不假定所有 packed texture 都是 ORM。
