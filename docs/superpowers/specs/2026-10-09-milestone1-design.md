## A1：Fab 的 UE 格式策略与反馈

核查发现：`fetch_metadata` 的格式详情请求只读取 UE 版本，但 `metadata_from_listing` 仍从全部 `assetFormats` 收集软件和格式字段。因此，“版本与格式都只采用 UE”的特征化测试在当前代码上应先失败，不能声称已存在这一完整行为。

用户选择：统一为 UE 格式策略。

- 新读取商品时，仅从 `unreal-engine` 条目收集版本、软件及格式信息。
- 商品含非 UE 格式时，提示 `该商品还包含非 UE 格式，已忽略：<格式代码列表>`；重复格式代码不重复显示，输出顺序稳定。
- 纯 UE 商品不增加提示；未标识格式不被误认为 UE。
- 优先沿用现有警告通道；必要时增加可选 `FabMetadata.format_warning` 及对应前端字段，不升级数据库。
- 手动读取时显示提示，后续保存结果也保留这一提示；后端直接读取的单条保存走 `single_import_warnings`，批量导入走逐行 `messages`。
- 本次不批量改写已存在素材的格式字段。

验收：混合格式只采用 UE 信息；非 UE 提示贯通单条读取、保存和批量报告；纯 UE 无新增提示；HTTP 安全规则不变。

## A2：定位商品前检查 Epic Launcher

在 `check_epic_protocol()` 成功之后、发送任何导航之前检查目标进程。普通定位和恢复定位共用这一检查。

- Windows 使用标准库调用 `tasklist`，按 `EpicGamesLauncher.exe` 过滤，CSV 输出，使用 `CREATE_NO_WINDOW`，不弹出命令窗口。
- 解析函数仅判断目标进程名是否存在，忽略大小写，不依赖中英文“无任务”提示。
- 确认未运行时返回 `Epic Games Launcher 未运行，请先启动 Epic 并登录后再定位商品`，不发送协议请求，也不尝试自动启动。
- 检测命令失败时保持现有行为，不将检测失败当作“未运行”。
- 已运行时保持原有普通定位和恢复定位顺序、并发保护及安全校验。

验收：目标 CSV、空输出、中文无任务、大小写和仅相似进程五类测试通过；已有三个导航测试通过；另保留 Windows 人工验收步骤。

## A3：只读翻译估算和发送前预览

用户选择：采用保守区间，预计超限时阻止在线提交，但仍能保存原文。

### 计算与保护

- 输入支持素材 ID 列表或当前表单本地化字段，计算实际缺失且有来源的目标字段，不把已有双语内容计入。
- 沿用 `missing_request`、术语保护、分段、标签直译和当前服务顺序；只读取适用服务的缓存，不把其他服务的缓存误当本次命中。
- 返回待补字段数、待翻译字符数、缓存命中片段数、Token 区间、本月已用、本月上限和预计超限信息；批量结果另包含可处理与跳过条目的摘要。
- 估算与正常请求的保守预留值量级一致。响应使用量、服务降级和额外重试存在不确定性，须明确标注；估算不等于官方账单或余额。
- 不调用会写缓存命中统计、额度预留、用量结算或在线请求的路径。重复估算不能改变 `usage()` 或缓存内容。
- 缓存关闭时不计入缓存命中；无适用服务时显示“不会产生在线请求”。
- “开关关闭”指当前操作适用的自动补译开关，不改变原有手动翻译或普通素材的翻译触发规则。百度单独启用时显示其字符估算，不能因 DeepSeek Token 为零而称无在线请求。
- 估算不是预约额度：发送时仍执行原有后端额度保护，处理估算后其他任务已消耗额度的情况。

### 单条保存与批量补译

- 单条保存前展示缺失字段和预计用量，使用“预计补译 X 个字段，约占本月额度 Y%”等清晰中文，不覆盖已有内容。
- 在线发送被预计超限阻止时，仍提供只保存原文的路径，不误导为已完成双语。
- 批量补译发送前使用确认面板，展示条目数、将被跳过的条目、待补字段、缓存和预计用量；超限时禁用在线发送并提供调整服务、额度或批次数量的明确提示。
- 估算等待、读取失败、无适用服务和全部缓存命中为不同状态，不以失败时的空数据冒充零费用。
- 前端复用现有配色、面板和加载反馈；支持键盘、取消及明确的禁用原因，等待时避免重复提交，过期估算不能用于新输入。

验收：全部缓存命中为零在线估算、超限判断正确、估算前后用量与缓存不变、服务未配置和关闭开关提示正确；确认面板、超限禁用及原文保存路径有前端覆盖；CI 不调用真实翻译服务。

## A4：每个实际打开素材库的升级前元数据库快照

用户选择：每个实际打开的已有素材库，每版本成功备份一次；新空库跳过，不扫描未打开的库。仅备份数据库，默认保留五份，与完整备份区分。

### 执行时点与记录

- 当前 `ensure_library` 与 `open_library` 都可进入 `db::open_database`，而后者会迁移数据库。因此备份必须放在所有实际既有库的迁移入口之前，不放在窗口打开之后。
- 先建立不执行迁移的 SQLite 连接，创建并校验快照，再进入现有数据库初始化和迁移。
- 比较 `env!("CARGO_PKG_VERSION")`，带默认值的 `last_backup_app_version` 与 `auto_backup_keep` 保留任务书要求；补充兼容旧设置的逐库记录，避免一个全局版本让第二个旧库漏备份。
- `auto_backup_keep` 默认 5，输入范围 1–20；不得改变已有定时完整备份的开关、周期或保留策略。
- 仅成功校验的快照允许更新该库版本记录。设置记录保存失败同样不能宣称已记录成功，应提示并允许下次重试。

### 复制、校验与保留

- 对已打开但未迁移的数据库使用 `VACUUM INTO`，不能直接复制运行中的数据库文件。
- 在素材库同级的专用自动备份目录保存含时间、应用版本和唯一标识的文件，不包含媒体、图片及其他大型附件。
- 使用只读连接执行 `PRAGMA integrity_check`，仅结果为 `ok` 才视为成功。
- 备份或校验失败时保留失败文件、不更新成功版本记录，通过 `startup_warning` 提示，下一次打开可重试，不因备份失败阻止启动。
- 清理只识别该库、该功能自行创建并符合完整命名约定的成功快照；超限时仅删除最旧快照，用户手动备份、其他库文件及失败快照不受清理影响。
- 设置页显示保留份数和当前库最近一次备份的时间与结果；失败信息包含可行的处理提示。

### 恢复边界

这些文件是升级前数据库快照，不是包含媒体的 `.dccassetlib` 完整备份包，现有完整备份导入不把裸数据库当作完整包。最终报告必须说明差异、用途和安全恢复步骤；本次不另建数据库快照恢复界面。完整备份、媒体文件和现有恢复流程保持原状。

验收：同版本跳过、不同版本一次、随后打开第二个旧库也受保护、新空库跳过、校验失败不记录版本、备份失败启动继续、只清理最旧自有快照、手动及其他库备份保留、旧设置兼容；另提供升级与恢复的 Windows 人工验收步骤。
