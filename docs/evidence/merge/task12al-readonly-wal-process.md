# 只读 WAL 的进程隔离实验

2026-11-01。全部实验使用临时合成数据库；没有读取真实用户数据，也没有增加产品来源读取入口。映流现有资料确认尚无专门的历史迁移导出命令，不能以其会迁移或恢复任务的普通服务构造器代替只读导出。

使用相同探针分别运行 SQLite 3.46.0 和 3.54.1：当写连接仍在**同一进程**时，即使读取连接使用 `mode=ro&readonly_shm=1`，两版本均完成备份但 SHM 字节发生变化，主库和 WAL 字节未变。把读取连接放到**独立进程**后，写连接保持打开但不写入、以及写连接已关闭这两组样本均能读到仅存在于 WAL 的记录并完成备份，三文件字节均未变化。这是当前 Windows 环境和这些样本下的观察，不能证明所有同进程或跨进程情况；结果与进程内共享 SHM 句柄有关是合理推测，不是已证明的唯一原因。

单独的并发探针让写连接在子进程存活期间提交 10 次，快照中两个关联数值一致。由于写连接本身会改变 WAL/SHM，该探针不能用文件前后差异证明读取端未写入。新增自动回归进一步在**第一次备份步骤完成之后、下一步之前**协调写连接提交 10 次，验证独立只读进程直接调用 SQLite 备份并得到 `(10, 10)`；另一项自动测试在写端空闲时通过既有快照函数比较主库、WAL 和 SHM 的完整字节。后者结合现有目录及三文件租约，在持有租约期间对三个合成文件的重命名均失败。子进程有超时终止和合成目录标记，所有文件均在临时目录。

学习迁入专项 184 项通过，最终日志 `release-artifacts/yingliu-merge/readonly-shm-learning-leased.log`；进程间并发专项日志 `readonly-shm-concurrent-test.log`，文件租约专项日志 `readonly-shm-lease-test.log`。两个 SQLite 版本的实验程序及日志位于 `release-artifacts/yingliu-merge/readonly-wal-probe*`、`readonly-wal-final-*` 和 `readonly-wal-concurrent-*`。本次未重复完整后端或前端回归。

此前 `task12c12` 在另一组条件下观察到 `readonly_shm=1` 的备份超时；本次不同夹具成功，不能据此断言该情形已被修复。SQLite 官方说明[只读 WAL 数据库仍依赖侧文件或其他特定条件](https://www.sqlite.org/wal.html#read_only_databases)。来源选择和撤销、文件身份与路径竞争、侧文件缺失或关闭竞争、损坏数据库、辅助进程的安全打包与终止、资源限制，以及真实源软件的 SQLite 版本仍需处理和验证。不能仅凭本实验开放真实来源读取；未完成原生桌面验收，未合并 main。
